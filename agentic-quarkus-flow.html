Aplicações AI-Infused

O que isso significa?

É fazer com que a IA faça parte do seu dia a dia, fazendo parte da solução que resolve problemas do seu negócio.

Começando pelos termos: aplicações AI-Infused são aplicações onde a IA faz parte da solução que resolve problemas do negócio, não algo separado.

Como usamos IA no dia a dia?

O jeito mais comum é a aplicação se comunicando com LLMs. No mundo Java, temos frameworks que fazem isso pra gente:

  • LangChain4j
  • Spring AI
  • Embabel

Aqui, vamos focar no LangChain4j com Quarkus.

Como desenvolvedores, o jeito mais comum de usar IA é nos comunicando com LLMs. No Java temos LangChain4j, Spring AI e Embabel. Nosso foco será LangChain4j com Quarkus.

<dependency>

Com Quarkus LangChain4j, basta adicionar a dependência do provedor que você quer usar: OpenAI, Ollama, watsonx, etc.

E uma interface na sua aplicação


@RegisterAiService
public interface DoctorAiService {

    String ask(String message);

}
Basta adicionar uma interface anotada com @RegisterAiService e o Quarkus gera a implementação que conversa com a LLM.

Mas você precisa de prompts

Prompts guiam a LLM a ser o mais precisa possível, evitando ambiguidade (engenharia de prompt). 


@RegisterAiService
public interface DoctorAiService {

    @SystemMessage("You are a medical expert...")
    @UserMessage("{message}")
    String ask(String message);

}
Só que a interface sozinha não basta: você precisa de prompts bem construídos, guiando a LLM da forma mais precisa e menos ambígua possível. @SystemMessage define o papel, @UserMessage a entrada.

LLMs são stateless

Cada requisição é uma nova requisição: você precisa manter o estado da conversação com a LLM. 


@RegisterAiService
public interface DoctorAiService {

    @SystemMessage("You are a medical expert...")
    @UserMessage("{message}")
    String ask(@MemoryId String sessionId, String message);

}
LLMs são stateless: cada requisição é independente. Para manter o contexto da conversa, usamos @MemoryId, que identifica a sessão e permite ao LangChain4j manter a memória da conversação.

Tools

LLMs não são determinísticas e não sabem executar tarefas específicas do seu negócio. Com tools, a LLM executa operações de forma determinística, usando o seu código. 


public class AgendaTools {

    @Inject
    AgendaRepository repo;

	  @Tool("get available agenda")
    public Agenda getAgenda() {
        return repo.availableAgenda();
    }

}
LLMs não são determinísticas e também não sabem como executar tarefas específicas do seu negócio e aplicação. Declarando tools, a LLM pode executar uma operação de forma determinística, utilizando o seu código.

Tools

Basta registrar a classe de tools no seu AI Service: 


@RegisterAiService(tools = {AgendaTools.class})
public interface DoctorAiService {

    @SystemMessage("You are a medical expert...")
    @UserMessage("{message}")
    String ask(@MemoryId String sessionId, String message);

}
Para disponibilizar as tools para a LLM, basta registrá-las no AI Service através do atributo tools do @RegisterAiService.

RAG

Retrieval-Augmented Generation: documentos e informações da que dão contexto à LLM.

1. Ingestão 📄 Docs, políticas, ..., e FAQs → 🗄️ Base de conhecimento
2. Consulta Prompt → 🔍 Busca → LLM + contexto → ✅ Resposta
RAG: a LLM não conhece os dados da sua empresa. Com RAG, você ingere documentos e informações do negócio (políticas, manuais, FAQs) em uma base de conhecimento, tipicamente um vector store com busca semântica. A cada pergunta, os trechos relevantes são recuperados e enviados junto, dando contexto à LLM. A resposta vem fundamentada nos seus dados, reduzindo alucinação.

Guardrails

Validam a entrada (prompt injection) e a saída (alucinação, conteúdo inadequado) do seu AI Service. 


@RegisterAiService(tools = {AgendaTools.class})
public interface DoctorAiService {

    @InputGuardrails(PromptInjectionGuard.class)
    @OutputGuardrails(MedicalAnswerGuard.class)
    String ask(@MemoryId String sessionId, String message);

}

Um guardrail pode resultar em:

success fatal retry reprompt
Guardrails são mecanismos de segurança: input guardrails validam a entrada do usuário antes de chegar à LLM (ex.: prompt injection); output guardrails validam a resposta antes de chegar ao usuário (ex.: alucinação, conteúdo inadequado). São beans CDI, declarados com @InputGuardrails e @OutputGuardrails. O resultado pode ser success, fatal, retry (regenera a resposta, máximo de tentativas configurável) ou reprompt (ajusta o prompt e tenta de novo).

Isso é a base

Mas para sistemas mais complexos, esses padrões sozinhos provavelmente não são suficientes…

…ou existe algo mais adequado?

Esses quatro padrões são a base de qualquer sistema agêntico. Mas quando o sistema cresce — falhas, estado, longa duração, humanos no meio do caminho — só esses padrões provavelmente não bastam. Precisamos de algo mais adequado: é aqui que entra a orquestração com Quarkus Flow.

Agentic Systems

De um AI Service para um sistema de agentes colaborando.

Transição: até aqui falamos de um único AI Service com prompts, memória, tools, RAG e guardrails. Agora vamos subir um nível: sistemas agênticos, onde vários agentes colaboram para resolver um problema.

4 padrões base de agentes

Sequence

Agent A → Agent B → Agent C

um após o outro, a saída vira entrada

Parallel

→ Agent A Agent B →

ao mesmo tempo, resultados combinados

Loop

Agent ↻ até a condição

repete até o resultado ser bom o suficiente

Conditional

condição? → Agent A Agent B

o caminho depende de uma condição

Os quatro padrões base de sistemas agênticos: Sequence (agentes em série, a saída de um vira entrada do outro), Parallel (agentes ao mesmo tempo, com resultados combinados), Loop (repete um agente até uma condição ser satisfeita) e Conditional (escolhe o agente conforme uma condição).

Workflows vs Agents

Workflow

Agents são programaticamente orquestrados através de um caminho predefinido

Agents

Agents direcionam dinamicamente sua própria ordem de invocação e têm controle sobre como executam as tarefas

Diferença entre workflows (orquestração predefinida) e agents (decisão dinâmica).

Por que agentes precisam de workflows duráveis?

  • Chamadas para LLMs falham, demoram e custam caro
  • Human-in-the-loop pode levar horas ou dias
  • Estado precisa sobreviver a restarts e deploys
  • Observabilidade: o que o agente decidiu e por quê?
Motivação: agentes em produção precisam de durabilidade, resiliência e observabilidade.

Tipos de Agents Workflows

  • @SequenceAgent permite você executar agentes de forma sequencial
  • @ParallelAgent permite você executar diversos agentes ao mesmo tempo
  • @LoopAgent como um for-loop no Java, permite você executar agentes até uma dada condição for satisfeita
  • @ConditionalAgent permite você dado uma condição utilizar ou não um agente
  • @HumanInTheLoop permite de forma programática pegar um input ou feedback de um humano
  • Non-AI agents permite com que você escreva código para performar alguma tarefa
Diferentes tipos de agents disponíveis: sequencial, paralelo, loop, condicional, human-in-the-loop e non-AI agents.

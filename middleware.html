Middleware

L'histoire d'une application qui grandit

Fil rouge du cours : on part d'une application toute simple, et on ajoute un middleware chaque fois qu'un problème concret apparaît. Les étudiants doivent repartir avec le réflexe « quel problème ce composant résout-il ? ».

C'est quoi un middleware ?

  • Un logiciel qui se place entre notre application et le reste du monde
  • Ce n'est pas notre code métier, mais notre application ne tourne pas sans
  • Il répond à un problème : trafic, stockage, communication entre services
Demander d'abord à la salle s'ils en connaissent un. Exemples attendus : Nginx, PostgreSQL, RabbitMQ, Redis. Une base de données est un middleware : on ne l'écrit pas, mais l'application ne marche pas sans.

Un serveur, une application, une base. Tout va bien… pour l'instant.

L'application fictive de tout le cours : une épicerie en ligne avec des commandes, un catalogue, des paniers et des chambres froides équipées de capteurs. Au départ, tout tient sur un seul serveur.

Au programme

  1. Le site est saturé : load balancer
  2. Plusieurs applications, un seul domaine : reverse proxy
  3. Des données de toutes les formes : bases de données
  4. Des services qui doivent se parler : messaging
Les quatre actes suivent la croissance de FraisDirect. Chaque acte commence par un problème, puis présente le middleware qui le résout.

1. Le Black Friday

Le problème

  • Le trafic est multiplié par 10 : le serveur sature
  • Le serveur redémarre pour une mise à jour : le site est coupé

Il faut plusieurs instances de l'application… et quelqu'un pour répartir les requêtes.

Deux problèmes différents : la capacité (trop de requêtes) et la disponibilité (le site coupé pendant une mise à jour). La même solution règle les deux : plusieurs instances.

Load Balancing

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							User -->|Requêtes 1, 2, 3| LoadBalancer
							LoadBalancer -->|Requête 1| Server1
							LoadBalancer -->|Requête 2| Server2
							LoadBalancer -->|Requête 3| Server3
Le load balancer est le seul point d'entrée connu des clients. Il distribue les requêtes entre les instances. Il ne doit pas devenir lui-même un point unique de panne : en production, on en met deux (actif/passif, IP virtuelle avec keepalived par exemple).

Load Balancing : gestion des pannes

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							classDef classAlert fill:red,color:white,stroke-width:2px,stroke:darkRed;

							User -->|Requêtes 1, 2, 3| LoadBalancer
							LoadBalancer -->|Requête 1| Server1
							LoadBalancer -->|Requêtes 2, 3| Server2
							LoadBalancer -.->|health check KO| Server3

							class Server3 classAlert;

Le load balancer interroge régulièrement chaque instance (health check) et retire celles qui ne répondent plus.

Le health check, c'est par exemple un GET /actuator/health toutes les quelques secondes. Après plusieurs échecs, l'instance est retirée ; elle revient quand elle répond de nouveau. C'est aussi ce qui permet de mettre à jour les instances une par une sans coupure (rolling update).

Répartir les requêtes

  • Round robin : chacun son tour
  • Least connections : vers l'instance la moins chargée
  • Hash (IP, cookie…) : toujours la même instance pour un même client

Niveau 4 (TCP) : le LB ne voit que des connexions. Niveau 7 (HTTP) : il peut router selon l'URL, les headers…

Round robin convient quand toutes les requêtes se ressemblent. Least connections est utile quand certaines requêtes sont longues. Le hash sert à garder un client sur la même instance, ce qui amène la question suivante. Niveau 4 : plus rapide mais aveugle. Niveau 7 : il lit le HTTP, donc il peut faire du routage par URL, ce qui ressemble déjà au reverse proxy.

Le panier est gardé en mémoire dans la session HTTP de l'application. Avec 3 instances derrière un load balancer en round robin, ça marche ?

Réponse : non. La requête suivante arrive sur une autre instance, qui ne connaît pas la session : le panier semble vide une fois sur trois.

Une application derrière un LB est stateless

  • La requête suivante arrive sur une autre instance : le panier a disparu
  • Sticky sessions (hash) : ça dépanne, mais le panier est perdu si l'instance tombe
  • La bonne solution : stocker l'état hors de l'application (on y revient avec les bases clé-valeur)
Les sticky sessions sont une rustine : la charge est mal répartie, et l'instance qui tombe emporte ses paniers. La vraie solution : session dans Redis (Spring Session) ou jeton côté client. On y revient dans l'acte 3 avec les bases clé-valeur.

Des load balancers

  • HAProxy, Nginx, Envoy : open source
  • F5 : propriétaire, matériel
  • Les LB des clouds (AWS ELB, Google Cloud Load Balancing…)
  • Le Service Kubernetes
En pratique, les étudiants utiliseront surtout le LB de leur cloud ou le Service Kubernetes, sans l'installer eux-mêmes. HAProxy et Nginx restent les références quand on gère ses propres serveurs.

2. Un site, plusieurs applications

Le problème

  • FraisDirect a maintenant un site vitrine, un front et une API
  • Trois applications, mais un seul point d'entrée pour les clients
  • Et un certificat HTTPS à gérer… trois fois ?
On ne veut pas exposer trois ports ou trois serveurs aux clients. On veut une seule adresse, un seul certificat, et décider derrière où va chaque requête.

Reverse Proxy

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							User --> Reverse[Reverse Proxy]
							Reverse -->|www.fraisdirect.fr| Vitrine[Site vitrine]
							Reverse -->|app.fraisdirect.fr| Front
							Reverse -->|app.fraisdirect.fr/api| API

Il route chaque requête selon le nom de domaine et le chemin.

Le client ne sait pas qu'il y a trois applications. Router /api vers le backend sur le même domaine que le front évite aussi les problèmes de CORS.

Les autres fonctionnalités

  • Terminaison HTTPS : un seul endroit pour les certificats
  • Authentification
  • Cache et compression
  • Limitation du nombre de requêtes (rate limiting)

Un reverse proxy spécialisé pour les API s'appelle une API gateway.

La terminaison HTTPS : le chiffrement s'arrête au reverse proxy, et les applications derrière parlent HTTP sur le réseau interne. Traefik et Caddy obtiennent les certificats Let's Encrypt automatiquement. API gateway : Kong, Spring Cloud Gateway, celles des clouds.

Des reverse proxys

  • Nginx
  • Traefik
  • Caddy
  • HAProxy
  • Apache
Nginx est le plus répandu. Traefik est très utilisé avec Docker et Kubernetes, car il se configure à partir des labels des conteneurs. Caddy est le plus simple à démarrer.

Load balancer ou reverse proxy ?

  • En général, les LB savent faire RP et les RP savent faire LB
  • Mais les objectifs sont différents :
  • Le RP répond aux préoccupations des DEV : l'architecture de l'application
  • Le LB répond aux préoccupations des OPS : la montée en charge, les coupures
Techniquement, c'est souvent le même logiciel (Nginx fait les deux). La différence est dans l'intention : découper l'application en plusieurs services (DEV), ou tenir la charge et les pannes (OPS).

Ajouter une 2ᵉ instance de l'application pour encaisser le pic du Black Friday : c'est d'abord le rôle…

  • A. du reverse proxy (préoccupation DEV)
  • B. du load balancer (préoccupation OPS)
Réponse : B. Ajouter des instances d'une même application pour tenir la charge, c'est le rôle du load balancer.

3. Des données de toutes les formes

Les besoins de FraisDirect

  • Les commandes et les factures
  • Un catalogue de produits où l'on cherche facilement
  • Les paniers, partagés entre les instances
  • La température des chambres froides
  • Les photos des produits et les factures PDF

Chaque besoin a son type de base.

Faire deviner aux étudiants, pour chaque besoin, si PostgreSQL convient. Pour les commandes, oui ; pour les autres, la réponse est moins évidente, et c'est le sujet de l'acte.

Commandes et factures : relationnel

Avantages Inconvénients
Transactions ACID Schéma rigide : chaque changement est une migration
Jointures et contraintes d'intégrité Difficile à répartir sur plusieurs serveurs
SQL : un langage standard Recherche textuelle limitée
Très répandu, très outillé

PostgreSQL, MySQL / MariaDB, Oracle, SQL Server

C'est le choix par défaut. Une commande, ses lignes, le client et la facture doivent rester cohérents : les transactions et les contraintes d'intégrité sont faites pour ça. Le schéma rigide est aussi une force : la base refuse les données incohérentes.

Le catalogue : document

Avantages Inconvénients
Schéma flexible : chaque produit a ses attributs Jointures limitées : on duplique les données
Recherche avancée (fautes de frappe, filtres) Transactions plus limitées et plus coûteuses
Se répartit facilement sur plusieurs serveurs

MongoDB, CouchDB, Elasticsearch / OpenSearch (moteurs de recherche)

Un fromage a une durée d'affinage, un fruit une origine et un calibre : en relationnel, ces attributs variables deviennent pénibles. Elasticsearch est d'abord un moteur de recherche : il ne remplace pas la base principale, on l'alimente à partir d'elle. MongoDB gère les transactions multi-documents depuis la version 4.0, mais ce n'est pas son point fort.

Les paniers : clé-valeur

Avantages Inconvénients
Très rapide (souvent en mémoire) On ne lit qu'à partir de la clé : pas de recherche
Simple à utiliser Pas de jointures
Expiration automatique des clés La persistance sur disque est à configurer

Redis / Valkey, Memcached (cache), etcd (configuration)

Retour sur l'acte 1 : c'est ici que l'on range les paniers pour que l'application soit stateless. Redis sert aussi de cache.

La température d'un capteur, relevée toutes les 10 secondes pendant un an : quel type de BDD ?

  • A. Relationnel
  • B. Document
  • C. Timeseries
  • D. Clé-valeur
Réponse : C. Environ 3 millions de mesures par capteur et par an, toujours lues par plage de temps. Une base relationnelle tient le coup au début, mais la timeseries compresse et agrège bien mieux.

Les chambres froides : timeseries

Avantages Inconvénients
Compression des mesures Très spécialisée
Agrégations dans le temps (moyenne par heure…) Pas faite pour modifier les données
Rétention : les vieilles données sont résumées puis supprimées

InfluxDB, TimescaleDB, Prometheus, VictoriaMetrics

Typiquement : alerte si la température dépasse 4 °C pendant plus de 10 minutes, graphique de la semaine. Prometheus est surtout utilisé pour la supervision des applications, avec sa propre base timeseries. TimescaleDB est une extension de PostgreSQL : pratique si PostgreSQL est déjà en place.

Photos et PDF : object storage

  • Stocke des fichiers (objets) rangés dans des buckets
  • Accès en HTTP, quasiment sans limite de taille
  • On remplace un objet, on ne le modifie pas

AWS S3 (et son API, devenue un standard), Google Cloud Storage, Azure Blob
Auto-hébergés : Ceph, Garage, SeaweedFS, MinIO

Les fichiers ne vont ni en base ni sur le disque du serveur : avec plusieurs instances, le disque local n'est pas partagé. Un bucket est un conteneur d'objets, pas un synonyme d'object storage. MinIO a beaucoup réduit son édition communautaire en 2025, d'où les alternatives citées.

Et pour les gros volumes : colonne

  • Wide-column (Cassandra, ScyllaDB, HBase, Bigtable) : énormément d'écritures, réparties sur de nombreux serveurs
  • Colonne analytique (ClickHouse, BigQuery) : statistiques sur des milliards de lignes
  • On modélise à partir des requêtes, et c'est complexe à exploiter

FraisDirect n'en a pas besoin… pour l'instant.

Deux familles qui partagent le même nom. Wide-column : on conçoit les tables à partir des requêtes, pas à partir des données. Colonne analytique : on lit quelques colonnes sur énormément de lignes, idéal pour les statistiques. À présenter rapidement : peu d'étudiants en auront besoin tôt.

Type Usage Exemple

Clé-valeur Cache, sessions Redis

Une application avec peu de trafic, beaucoup de règles métier et une recherche par nom de produit : quel type de SGBD choisir ?

  • A. Relationnel
  • B. Document
  • C. Colonne
  • D. Clé-valeur
Réponse : A. Peu de trafic et beaucoup de règles métier : relationnel. Une recherche par nom se fait très bien en SQL ou avec la recherche plein texte de PostgreSQL. Ceux qui répondent B pensent à la recherche : c'est la transition vers la slide suivante.

Une base de plus, c'est un coût

  • Il faut l'installer, la sauvegarder, la surveiller, la mettre à jour
  • PostgreSQL sait déjà faire de la recherche plein texte et stocker du JSON
  • On commence simple, on ajoute une base spécialisée quand le besoin est réel
Le piège classique : une base par besoin dès le premier jour. Chaque base en plus, c'est une sauvegarde à faire, une version à mettre à jour, des données à garder synchronisées.

Quand le besoin est réel

Le catalogue grossit : il faut tolérer les fautes de frappe et filtrer par catégorie, prix, origine…

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							ServiceCatalogue -->|sql| PG[(PostgreSQL)]
							ServiceCatalogue -->|événement : produit modifié| ServiceRecherche

Comment ces événements circulent-ils ? C'est l'acte 4.

PostgreSQL reste la source de vérité ; Elasticsearch n'est qu'une copie pensée pour la recherche. Il faut donc propager chaque modification : c'est le rôle des événements, et la transition vers le messaging.

Bonnes pratiques

  • Une base ne se partage pas entre applications différentes
  • Une base se sauvegarde… et on teste la restauration
  • Le schéma évolue par migrations versionnées (Flyway, Liquibase)
  • La bonne base pour le bon usage, mais pas une de plus que nécessaire
Base partagée entre applications : le schéma devient un contrat que personne ne peut plus modifier. Une sauvegarde dont on n'a jamais testé la restauration ne compte pas. Migrations : le schéma est versionné avec le code et appliqué automatiquement au démarrage.

4. Des services qui doivent se parler

Le problème

Quand une commande est validée, il faut :

  • envoyer un email de confirmation
  • générer la facture
  • prévenir l'entrepôt

En appels HTTP directs : le client attend tout, et si le service d'email est en panne… la commande échoue.

Faire chiffrer le temps : 200 ms pour l'email, 1 s pour le PDF, 300 ms pour l'entrepôt ; le client attend tout ça. Et une panne du service d'email ne devrait pas empêcher de vendre.

Un broker de messages

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							Commande[Service commande] -->|commande créée| Broker{{Broker}}
							Broker --> Email[Service email]
							Broker --> Facture[Service facture]
							Broker --> Entrepot[Service entrepôt]
  • Découplage : le service commande ne connaît pas ses consommateurs
  • Asynchrone : la commande est validée tout de suite
  • Résilience : si un service est en panne, ses messages l'attendent
Le service commande annonce un fait (« une commande a été créée ») ; il ne donne pas d'ordre. Ajouter un service intéressé, la fidélité par exemple, ne demande aucune modification du service commande.

Absorber les pics

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							Producer -->|produit 1 à 40 messages/s| Queue
							Queue -->|consomme 10 messages/s| Consumer

Pendant le pic, la file se remplit. Après, le consumer rattrape son retard. Rien n'est perdu.

Le broker sert de tampon. Si le consumer est durablement plus lent que le producer, la file grossit sans fin : il faut alors ajouter des consumers. Surveiller la taille des files fait partie de l'exploitation.

Le vocabulaire AMQP

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							Producer -->|routing key| Exchange{{Exchange}}
							Exchange -->|binding| Q1[Queue facturation]
							Exchange -->|binding| Q2[Queue entrepôt]
							Q1 --> C1[Consumer facturation]
							Q2 --> C2[Consumer entrepôt]
  • Le producer publie sur un exchange, avec une routing key
  • L'exchange copie le message dans chaque queue dont le binding correspond
  • Le consumer lit une queue
Point important : le producer ne publie jamais directement dans une queue, il publie sur un exchange. Le routage se fait dans l'exchange, grâce aux bindings. Types d'exchange : direct (clé exacte), topic (motifs), fanout (toutes les queues liées).

Topic exchange

Routing key publiée : commande.creee.fr

  • * remplace exactement un mot
  • # remplace zéro ou plusieurs mots
Binding Reçoit commande.creee.fr ?
commande.# Oui
*.creee.* Oui
#.fr Oui
commande.* Non
Les routing keys sont des mots séparés par des points. Les motifs ne sont pas des expressions régulières. commande.* ne matche pas commande.creee.fr, car * remplace exactement un mot.

Une queue est liée avec le binding commande.*. Quels messages reçoit-elle ?

  • A. commande.creee seulement
  • B. commande.creee.fr seulement
  • C. Les deux
  • D. Aucun des deux
Réponse : A. * remplace exactement un mot. Pour recevoir les deux, il faudrait commande.#.

Plusieurs consumers sur une queue

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							Exchange{{Exchange}} --> Q1[Queue facturation]
							Exchange --> Q2[Queue entrepôt]
							Q1 -->|message 1| F1[Facturation instance 1]
							Q1 -->|message 2| F2[Facturation instance 2]
							Q2 -->|messages 1 et 2| E1[Entrepôt]
  • Chaque queue reçoit sa copie du message
  • Les consumers d'une même queue se partagent les messages : chacun est traité une fois
Deux mécanismes à ne pas confondre : plusieurs queues, chaque service reçoit sa copie (diffusion) ; plusieurs consumers sur une même queue, les messages se répartissent entre eux (competing consumers). C'est ce qui permet de mettre le service de facturation derrière plusieurs instances, comme dans l'acte 1.

Queue ou log ?

Queue (RabbitMQ) Log (Kafka)
Le message est supprimé une fois traité Les messages sont conservés et peuvent être relus
Routage riche (exchanges, bindings) Ordre garanti par partition
Distribuer du travail Très gros débits, historique d'événements
Avec Kafka, chaque groupe de consumers garde sa position dans le log : un nouveau service peut relire tout l'historique. Avec RabbitMQ, un message traité disparaît. RabbitMQ propose aussi des streams, qui se rapprochent du log de Kafka.

Des brokers

  • RabbitMQ : protocole AMQP
  • Mosquitto : protocole MQTT, pour l'IoT (les capteurs des chambres froides)
  • Kafka
  • NATS, Pulsar
AMQP et MQTT sont des protocoles ; RabbitMQ, Mosquitto et Kafka sont des logiciels. RabbitMQ sait aussi parler MQTT. Dans FraisDirect, les capteurs publieraient en MQTT.

AMQP dans Spring

La dépendance :


implementation 'org.springframework.boot:spring-boot-starter-amqp'

Des messages en JSON plutôt qu'en texte :


@Bean
MessageConverter jsonMessageConverter() {
    return new Jackson2JsonMessageConverter();
}
Spring Boot branche automatiquement ce bean sur le RabbitTemplate et sur les listeners. Avec Spring Boot 4 (Jackson 3), la classe s'appelle JacksonJsonMessageConverter.

Déclarer exchange, queue et binding


@Configuration
public class RabbitConfiguration {

    public static final String FACTURATION_QUEUE = "facturation";

    @Bean
    TopicExchange fraisDirectExchange() {
        return new TopicExchange("fraisdirect", true, false);
    }

    @Bean
    Queue facturationQueue() {
        return QueueBuilder.durable(FACTURATION_QUEUE)
                .quorum()
                .build();
    }

    @Bean
    Binding facturationBinding(Queue facturationQueue, TopicExchange fraisDirectExchange) {
        return BindingBuilder.bind(facturationQueue)
                .to(fraisDirectExchange)
                .with("commande.creee.*");
    }
}
Spring déclare ces objets dans RabbitMQ au démarrage s'ils n'existent pas. durable : la queue survit au redémarrage du broker. quorum : la queue est répliquée sur plusieurs nœuds RabbitMQ ; c'est le type recommandé aujourd'hui. Le binding : la queue facturation reçoit toutes les commandes créées, quel que soit le pays.

Publier un message


@Service
public class CommandeService {

    private final RabbitTemplate rabbitTemplate;
    // ...

    public void valider(Commande commande) {
        commandeRepository.save(commande);
        rabbitTemplate.convertAndSend("fraisdirect",
                "commande.creee." + commande.pays(),
                new CommandeCreee(commande.id(), commande.montant()));
    }
}
convertAndSend : exchange, routing key, objet. Grâce au converter JSON, l'objet CommandeCreee est sérialisé en JSON. On envoie un événement avec les infos utiles, pas l'entité JPA. Garder en tête l'enchaînement save puis publication : on y revient à la fin de l'acte.

@Service
public class FacturationListener {

    private final FactureService factureService;

Le paramètre est désérialisé automatiquement depuis le JSON. Si la méthode se termine normalement, Spring confirme (ack) le message ; si elle lève une exception, le message est rejeté. C'est le sujet de la question qui suit l'exercice.

À vous : consommez la file commandes

Chaque message reçu (une chaîne) doit être passé à commandeService.traiter(...).

Réponse attendue : @RabbitListener(queues = "commandes") sur une méthode public void recevoir(String commande) { commandeService.traiter(commande); }. Erreurs fréquentes : oublier l'annotation, mettre le nom de l'exchange à la place de celui de la queue, retourner une valeur.

Avec Spring AMQP et une queue classique, que devient par défaut un message dont le traitement lève une exception dans le listener ?

  • A. Il est perdu
  • B. Il est rejoué à l'infini
  • C. Il part dans une dead letter queue
  • D. Il est renvoyé au producer
Réponse : B. Par défaut, Spring remet le message dans la queue (requeue) : il revient aussitôt, échoue de nouveau, et ainsi de suite. On parle de poison message : il occupe le consumer et remplit les logs.

Gestion des erreurs

  • Queue classique : le message est remis dans la queue et rejoué à l'infini
  • Quorum queue (RabbitMQ 4 et plus) : rejoué 20 fois, puis supprimé
  • Message illisible (erreur de conversion) : rejeté sans être rejoué

Dans tous les cas, on veut limiter les essais et garder les messages en échec pour les analyser.

Attention : notre configuration utilise une quorum queue. Depuis RabbitMQ 4.0, ces queues ont une delivery-limit de 20 par défaut : après 20 livraisons, le message est supprimé, ou envoyé en dead letter si c'est configuré. Le « rejoué à l'infini » ne vaut que pour les queues classiques.

Dead Letter Queue

							%%{init: {'theme': 'dark', 'themeVariables': { 'darkMode': true }}}%%
							graph LR
							Producer --> Exchange{{Exchange}}
							Exchange --> Queue
							Queue -->|erreur| Consumer
							Queue -->|rejeté| DLX{{Dead letter exchange}}
							DLX --> DLQ[Dead letter queue]

Un message rejeté passe par un dead letter exchange qui le range dans une queue dédiée.

La DLQ est une queue comme les autres : on peut la surveiller, lire les messages, corriger le bug puis les réinjecter. Une alerte sur la taille de la DLQ est indispensable, sinon personne ne la regarde.

Dead Letter Queue dans Spring


@Bean
Queue facturationQueue() {
    return QueueBuilder.durable(FACTURATION_QUEUE)
            .quorum()
            .deadLetterExchange("fraisdirect.dlx")
            .build();
}

Et quelques essais avant d'abandonner :


spring.rabbitmq.listener.simple.retry.enabled=true
spring.rabbitmq.listener.simple.retry.max-attempts=3
Il faut aussi déclarer l'exchange fraisdirect.dlx, la queue facturation.dlq et leur binding, comme sur la slide de configuration. Après les essais, Spring rejette le message sans le remettre en queue : il part dans la DLQ.

Un message peut arriver deux fois

  • Le consumer confirme (ack) le message une fois traité
  • S'il plante entre le traitement et l'ack, le message est rejoué
  • On parle de livraison at-least-once

Le consumer doit être idempotent : traiter deux fois la même commande ne doit pas générer deux factures.

Exactly-once n'existe pas vraiment en pratique ; on vise at-least-once avec des consumers idempotents. Exemple : avant de générer la facture, vérifier qu'il n'en existe pas déjà une pour cet identifiant de commande, avec une contrainte d'unicité en base.

Et du côté du producer ?

Dans valider : la commande est enregistrée, puis le message est publié.

Si l'application plante entre les deux, la commande existe mais personne n'est prévenu.

Le pattern outbox : on écrit le message dans une table, dans la même transaction que la commande, et un process le publie ensuite.

Le problème de la double écriture : la base et le broker ne partagent pas de transaction. Avec l'outbox, l'événement est enregistré dans la même transaction que la commande ; un process (planifié, ou Debezium qui lit les logs de la base) le publie ensuite. Le message peut être publié deux fois : d'où l'idempotence de la slide précédente.

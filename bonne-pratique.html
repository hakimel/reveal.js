Bonnes pratiques

Organiser son code pour qu'il reste facile à changer

Fil rouge : la banque en ligne des autres cours. Son code a grossi, et chaque modification devient plus risquée. On voit trois façons de garder le code facile à changer : découper les objets, designer l'API, ranger les packages.

Le code de la banque a grossi

  • Une classe Client de 40 champs
  • Un VirementService qui envoie aussi les mails et les relevés PDF
  • Une API qui renvoie tout, tout le temps
  • Un package service/ de 80 classes

Rien n'est faux. Mais chaque modification prend une journée.

Demander à la salle s'ils ont déjà vu ça en entreprise ou en projet. Chaque point correspond à une partie du cours.

Acte 1

Découper ses objets

Des classes petites, qui font une seule chose

On part d'un exercice qui a l'air simple et qui devient vite pénible si on l'aborde avec l'héritage.

Exercice

Petit exercice

  1. Implémenter un objet Afficheur avec une méthode afficher(String message) qui fait System.out.println(message)
  2. Ajouter une vérification : si le message contient un « a », on ne l'affiche pas
  3. Dans un main : deux afficheurs, un en minuscules et un en majuscules
  4. L'afficheur en majuscules vérifie aussi que le message fait 5 caractères
  5. Un troisième affiche normalement et vérifie uniquement la taille de 5
Dérouler une consigne à la fois, et laisser les étudiants coder après chacune. La dernière consigne est le piège : elle ne veut pas la vérification du « a ». Ceux qui ont fait de l'héritage doivent tout défaire. On garde leurs solutions pour la partie composition.

Les principes SOLID

S Single responsibility Une classe, une seule raison de changer
O Open/closed Ajouter un comportement sans modifier l'existant
L Liskov substitution Une sous-classe peut remplacer sa mère
I Interface segregation Des petites interfaces plutôt qu'une grosse
D Dependency inversion Dépendre d'interfaces, pas d'implémentations
Cinq principes, une phrase chacun. On ne détaille que le S, celui qu'on viole le plus souvent. Le D, ils l'ont déjà utilisé sans le savoir dans le cours sur les tests : c'est lui qui permet de passer un mock de CompteRepository ou de SepaClient à VirementService.

Une classe ClientService gère les clients, envoie les mails et génère les relevés PDF. Quel principe viole-t-elle surtout ?

  • A. S : Single responsibility
  • B. O : Open/closed
  • C. L : Liskov substitution
  • D. I : Interface segregation
  • E. D : Dependency inversion
Réponse A. Trois raisons de changer : les règles client, le contenu des mails, le format des relevés. Un changement de mise en page du relevé oblige à toucher la classe qui gère les clients.

S : découper un service

Lien avec le cours sur les tests : une classe qui fait trois choses a trois fois plus de dépendances à mocker. Une classe dure à tester est souvent une classe trop grosse.

S : les entités aussi

Les entités sont souvent la racine du problème


public class Client {
    private String nom;
    private String rue;
    private String ville;
    private String codePostal;
}

La rue, la ville et le code postal vont toujours ensemble…

Demander ce qu'ils remarquent. Trois champs qui n'ont de sens qu'ensemble : c'est un objet qui n'a pas encore de nom.

Étape 1 · Un groupe logique


public class Client {
    private String nom;
    private Adresse adresse;
}

public class Adresse {
    private String rue;
    private String ville;
    private String codePostal;
}
L'adresse devient un objet. La validation du code postal, par exemple, a maintenant une place évidente : dans Adresse.

Étape 2 · Le besoin change

La banque écrit au domicile, mais envoie les relevés ailleurs


public class Client {
    private String nom;
    private Adresse adressePostale;
    private Adresse adresseReleves;
}

Une ligne de plus, au lieu de quatre champs copiés.

Sans l'étape 1, il aurait fallu rueReleves, villeReleves, codePostalReleves… et dupliquer la validation. Le découpage paie dès le premier changement.

Étape 3 · Des rôles différents

Un client et un conseiller se connectent tous les deux


public class Utilisateur {
    private String nom;
    private String email;
    private String motDePasse;
}

public class Client {
    private Utilisateur utilisateur;
    private Adresse adressePostale;
}

public class Conseiller {
    private Utilisateur utilisateur;
    private String agence;
}
Client et Conseiller contiennent un Utilisateur, ils n'en héritent pas. C'est de la composition, le sujet de la suite.

Composition over inheritance

  • L'héritage n'est pas la solution pour factoriser du code
  • 90 % du temps, il est mal utilisé (source : moi)
Le réflexe classique : deux classes ont du code en commun, donc on crée une classe abstraite. On va voir pourquoi c'est rarement une bonne idée, et le cas où ça l'est.

Mauvais exemple


abstract class Notification {
    abstract void envoyer(Virement virement);

    protected String formaterMontant(long centimes) {
        return String.format("%d,%02d €",
                centimes / 100, centimes % 100);
    }
}

class NotificationMail extends Notification {
    void envoyer(Virement virement) {
        String montant = formaterMontant(virement.montant());
        // … envoie le mail
    }
}

La mère n'appelle jamais envoyer : elle sert juste de boîte à outils

Conséquence : ReleveService veut aussi formater un montant. Il doit hériter de Notification ? Non. Et en Java, on n'hérite que d'une seule classe. Le code partagé doit aller dans sa propre classe.

Bon exemple


abstract class Notification {
    final void notifier(Virement virement) {
        if (accepte(virement.client())) {
            envoyer(virement);
        }
    }

    abstract boolean accepte(Client client);
    abstract void envoyer(Virement virement);
}

class NotificationSms extends Notification {
    boolean accepte(Client client) {
        return client.accepteLesSms();
    }

    void envoyer(Virement virement) {
        // … envoie le SMS
    }
}
Ici la mère appelle les méthodes abstraites : elle définit le déroulé, les filles remplissent les trous. C'est le bon usage d'une classe abstraite (le patron « template method »).

Retour à l'afficheur

Le format et la vérification deviennent des objets


class Afficheur {
    private final Function<String, String> format;
    private final Predicate<String> verification;

    Afficheur(Function<String, String> format,
              Predicate<String> verification) {
        this.format = format;
        this.verification = verification;
    }

    void afficher(String message) {
        if (verification.test(message)) {
            System.out.println(format.apply(message));
        }
    }
}
Correction de l'exercice. Plus aucune sous-classe : un afficheur est assemblé à partir d'un format et d'une vérification.

Retour à l'afficheur


Predicate<String> sansA = m -> !m.contains("a");
Predicate<String> cinqCaracteres = m -> m.length() == 5;

var minuscule = new Afficheur(String::toLowerCase, sansA);

var majuscule = new Afficheur(
        String::toUpperCase,
        sansA.and(cinqCaracteres));

var normal = new Afficheur(
        Function.identity(), cinqCaracteres);

La consigne piège devient une ligne : on assemble autrement

Avec l'héritage, le troisième afficheur cassait toute la hiérarchie car il ne voulait pas la vérification du « a ». Avec la composition, on choisit les briques. Comparer avec les solutions des étudiants.

À retenir

  • Une classe, une seule raison de changer
  • Des champs qui vont ensemble forment un objet
  • Pour partager du code : une classe à part, injectée
  • Une classe abstraite seulement si la mère appelle les méthodes des filles
Le test simple : si la classe mère n'appelle jamais ses méthodes abstraites, l'héritage ne sert qu'à partager du code, et la composition fait mieux.

Acte 2

Designer son API REST

Ce que voit le front n'est pas ce qui est en base

L'API est un contrat avec le front et les autres équipes. Une fois publiée, elle est difficile à changer : autant la penser dès le début.

Retourner directement l'entité JPA Client (avec son mot de passe) depuis un @RestController, bonne idée ?

Réponse : non. Faire justifier les réponses avant de passer à la suite.

Ce qui se passe


@Entity
public class Client {
    @Id
    private Long id;
    private String email;
    private String motDePasse;
    @OneToMany(mappedBy = "client")
    private List<Compte> comptes;
}
  • Le hash du mot de passe part dans le JSON
  • Client → comptes → client → comptes… : sérialisation sans fin
  • Renommer une colonne casse le front
Les trois problèmes arrivent pour de vrai. Le deuxième se termine en StackOverflowError ou en LazyInitializationException. Le troisième est le plus sournois : le schéma de la base devient le contrat de l'API.

La solution : un DTO


public record ClientDto(Long id, String email) {}

@GetMapping("/clients/{id}")
public ClientDto trouver(@PathVariable Long id) {
    Client client = clientService.trouver(id);
    return new ClientDto(client.getId(), client.getEmail());
}
  • On choisit exactement ce qui sort
  • On maîtrise le schéma, et on peut le versionner
DTO : Data Transfer Object. Un record suffit. La conversion peut aussi se faire avec MapStruct, mais à la main c'est très bien pour commencer.

Découper les ressources

Un compte de la banque


public class Compte {
    private Long id;
    private String libelle;
    private Titulaire titulaire;
    private List<Beneficiaire> beneficiaires;
    private List<Operation> operations;
}
Un petit objet (le titulaire), une liste courte (les bénéficiaires), une liste qui peut devenir très longue (les opérations). Que renvoyer sur GET /comptes/12 ?

Mauvaise pratique

GET /comptes/12


{
  "id": 12,
  "libelle": "Compte courant",
  "titulaire": {
    "nom": "Alice"
  },
  "beneficiaires": [
    { "id": 7, "nom": "Bob" }
  ],
  "operations": [
    { "montant": -1200, "libelle": "Virement Bob" },
    …
  ]
}
Dérouler avec les fragments. Le titulaire, ça va. Les bénéficiaires et les opérations : le front qui veut juste afficher le libellé du compte télécharge 3 000 opérations.

Bonne pratique

GET /comptes/12


{
  "id": 12,
  "libelle": "Compte courant",
  "titulaire": {
    "nom": "Alice"
  }
}

GET /beneficiaires?compte=12


[
  { "id": 7, "nom": "Bob" }
]

GET /operations?compte=12


[
  { "montant": -1200, "libelle": "Virement Bob" }
]
Une ressource par URL. Le petit objet reste dans le compte, les listes ont leur propre URL, avec filtre et pagination. Le front appelle ce dont il a besoin.

Les verbes HTTP

Je veux Appel
Lire GET /virements/12
Chercher GET /virements?compte=42
Créer POST /virements
Modifier PUT /virements/12
Supprimer DELETE /virements/12
L'URL désigne la ressource, le verbe dit ce qu'on en fait.

Les verbes dans l'URL

  • Pour une action métier : POST /virements/12/annuler
  • /init : le POST suffit
  • /search : le GET suffit
  • /delete : le verbe HTTP existe
Annuler un virement programmé, ce n'est pas le supprimer : on le garde dans l'historique, on change son état, on prévient le client. C'est une action métier, un verbe dans l'URL est justifié. Pour le reste, les verbes HTTP suffisent.

Quel appel pour supprimer le bénéficiaire 12 ?

  • A. POST /beneficiaires/12/delete
  • B. DELETE /beneficiaires/12
  • C. GET /beneficiaires/delete?id=12
  • D. POST /beneficiaires/delete/12
Réponse B. La C est la pire : un GET ne doit jamais modifier quoi que ce soit, un robot d'indexation ou un préchargement du navigateur pourrait supprimer le bénéficiaire.

À retenir

  • Jamais d'entité dans un contrôleur : un DTO
  • Une ressource par URL, les listes à part
  • Le verbe HTTP dit l'action, sauf pour une action métier
Le DTO est aussi une question de sécurité : c'est lui qui garantit que le mot de passe ne sort pas.

Acte 3

Ranger ses packages

Trouver le code sans le chercher

Trois façons de ranger le même projet, de la plus courante à la plus utile.

Rangement 1 · Par couche

banque/
├─ config/
├─ controller/
├─ repository/
└─ service/
  • Simple pour démarrer
  • 80 classes dans service/
  • Toucher aux virements = ouvrir 4 dossiers
Le rangement de tous les tutoriels Spring. Très bien pour 10 classes, pénible à 200.

Rangement 2 · Par domaine

banque/
├─ compte/
│  ├─ controller/
│  ├─ repository/
│  └─ service/
├─ virement/
│  ├─ controller/
│  ├─ repository/
│  └─ service/
└─ notification/
   └─ …
  • Les éléments sont regroupés par domaine fonctionnel
  • On explore le projet par le métier
Un nouveau développeur qui doit corriger un bug sur les virements sait où aller. Et un domaine qui grossit peut devenir une application séparée plus facilement.

Rangement 3 · Domaine, entrées et sorties

virement/
├─ config/
├─ in/
│  ├─ controller/
│  └─ amqp/
├─ out/
│  ├─ repository/
│  └─ sepa/
└─ service/
  • in/ : ce qui appelle le domaine (HTTP, messages)
  • out/ : ce que le domaine appelle (base, API externes)
  • Les dépendances se voient
  • Les études d'impact sont plus faciles
Question d'étude d'impact : le réseau SEPA change son API, qu'est-ce qui est touché ? Uniquement out/sepa. Le listener RabbitMQ du cours middleware irait dans in/amqp.

À retenir

  • Ranger par domaine, pas par couche
  • Séparer ce qui entre et ce qui sort du domaine
  • Le but : trouver le code et mesurer l'impact d'un changement
Fin du cours. Les trois parties disent la même chose : du code découpé selon le métier est du code qu'on peut changer sans peur.

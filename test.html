Tester une application

Du test unitaire au test end-to-end

Premier cours de la série. On y présente la banque en ligne qui sert d'exemple : des comptes et des virements, qu'on retrouvera dans les cours suivants. Les étudiants connaissent déjà JUnit : on ne réexplique pas la syntaxe, on se concentre sur quoi tester, quand, et avec quel outil.

Notre application

Une banque en ligne : des comptes, des virements

							graph LR
							User[Client] --> App[Application Spring Boot]
							App --> PG[(PostgreSQL)]

On va la faire grandir dans les prochains cours. Aujourd'hui : s'assurer qu'elle marche.

Le fil rouge des cours. Ici, elle est encore petite : une application, une base. C'est aussi le code de l'exemple qu'on reprend en mob programming.

Une règle métier

Un virement est plafonné à 1 000 €

Un virement de 1 000 € pile est accepté

La règle qui va servir d'exemple pour tout le début du cours. Elle a l'air triviale, c'est voulu : même une règle de deux lignes cache un cas limite, on le verra en TDD.

Un lundi matin

  1. Un développeur ajoute les virements instantanés
  2. Il teste son virement instantané à la main : il marche
  3. Il met en production
  4. Les virements de 1 000 € pile sont refusés pour tout le monde
  5. On l'apprend une semaine plus tard, par le service client
Demander à la salle : qu'est-ce qui a manqué ? Il a testé ce qu'il a modifié, pas ce qui marchait déjà. C'est la définition d'une régression.

Pourquoi tester ?

Laisser l'image quelques secondes, puis passer à la réponse.

Pourquoi tester ?

  • Vérifier que les nouvelles fonctionnalités fonctionnent
  • Vérifier qu'il n'y a pas de régression : ce qui marchait marche toujours
Le deuxième point est le plus important et le plus oublié. Une fonctionnalité, on la teste au moins une fois à la main. Ce qui marchait déjà, personne ne le reteste.

Au programme

  1. Quand écrire ses tests : le TDD
  2. Tester une classe seule : tests unitaires, mocks et fakes
  3. Tester avec le framework et la base : tests d'intégration
  4. Tester comme un utilisateur : tests end-to-end
Les trois derniers points sont les trois étages de la pyramide qu'on va voir juste après.

Plus on monte, plus un test vérifie de choses d'un coup, mais plus il est lent à écrire, à exécuter et à réparer. D'où la forme : beaucoup de tests unitaires en bas, quelques tests end-to-end en haut. Les tests manuels ne disparaissent pas, ils deviennent rares.

Pourquoi on gagne du temps

À la main

  1. Démarrer l'application
  2. Créer deux comptes
  3. Faire un virement de 999,99 €
  4. Lire si le virement passe
  5. Recommencer à 1 000 €, à 1 200 €…

Avec des tests

  1. Lancer les tests

Quelques secondes, tous les cas d'un coup, à chaque modification.

Demander combien de temps prend la colonne de gauche : quelques minutes. Et on la refait à chaque modification, donc en pratique on ne la refait pas. C'est comme ça qu'arrivent les régressions du lundi matin.

Quand écrire ses tests ?

Une fonctionnalité, un bug

À la fin
Au premier bug
Avant le dev
Développement Écriture d'un test Test manuel Correction de bug À répéter à chaque bug
Lire ligne par ligne. Tests à la fin : chaque bug coûte une correction plus un test manuel complet. Au premier bug : on écrit le test à ce moment-là, ensuite le bug ne coûte plus que sa correction. Avant le dev : le test est déjà là, on ne fait le test manuel qu'une fois, à la fin. Pour un seul bug, les trois se valent à peu près.

Et si le bug revient trois fois ?

À la fin
Au premier bug
Avant le dev
Développement Écriture d'un test Test manuel Correction de bug À répéter à chaque bug
Les deux schémas sont à la même échelle. Avec les tests à la fin, chaque bug refait payer un test manuel complet. Avec le test écrit avant, un bug ne coûte que sa correction : le test dit tout de suite si c'est réparé. C'est l'argument du TDD, qui arrive juste après.

Acte 1

TDD

Test Driven Development : le test d'abord

On déroule le TDD sur la règle du plafond, en trois tours. Prendre le temps sur chaque tour : c'est le rythme qu'il faut faire sentir, pas le code, qui est trivial.

En TDD, par quoi commence-t-on ?

  • A. Écrire le code de la fonctionnalité
  • B. Écrire un test qui échoue
  • C. Refactorer le code existant
Réponse B. Poser la question avant d'expliquer : beaucoup répondent A, et c'est justement ce que le TDD inverse.

Le cycle

1. Écrire un test qui échoue → 2. Le faire passer, au plus simple → 3. Refactorer sans rien casser ↺
  • Rouge : le test échoue, il décrit ce qu'on veut
  • Vert : le minimum de code pour qu'il passe
  • Refactor : on nettoie, les tests protègent
Insister sur « le minimum ». Les étudiants voudront écrire toute la règle d'un coup. Le TDD, c'est des petits pas : chaque test ajoute une seule exigence.

Tour 1 · Rouge

Un virement de 300 € est accepté


class PlafondVirementTest {

    @Test
    void unVirementDe300EurosEstAccepte() {
        // Given : les montants sont en centimes
        long montant = 30000;
        // When
        boolean accepte = new PlafondVirement().accepte(montant);
        // Then
        assertTrue(accepte);
    }
}
Rappel JUnit au passage : Given / When / Then, un nom de test qui se lit comme une phrase. Les montants sont en centimes pour éviter les erreurs d'arrondi des double. La classe PlafondVirement n'existe pas encore : le test ne compile même pas. C'est rouge.

Tour 1 · Rouge

On crée la classe, juste pour que ça compile


class PlafondVirement {
    boolean accepte(long montant) {
        return false;
    }
}

✗ unVirementDe300EurosEstAccepte
expected: <true> but was: <false>

On lance le test et on le voit échouer, pour la bonne raison. Un test qu'on n'a jamais vu rouge peut très bien ne rien tester.

Tour 1 · Vert

Le minimum pour passer au vert


class PlafondVirement {
    boolean accepte(long montant) {
        return true;
    }
}

✓ unVirementDe300EurosEstAccepte

Les étudiants vont trouver ça ridicule, et c'est le but de la discussion : rien dans les tests ne demande autre chose pour l'instant. C'est le test suivant qui va forcer la vraie règle.

Tour 2 · Rouge

Un virement de 1 500 € est refusé


@Test
void unVirementDe1500EurosEstRefuse() {
    var plafond = new PlafondVirement();

    assertFalse(plafond.accepte(150000));
}

✗ unVirementDe1500EurosEstRefuse
expected: <false> but was: <true>

Le nouveau test échoue, le premier passe toujours.

Tour 2 · Vert


class PlafondVirement {
    boolean accepte(long montant) {
        return montant < 100000;
    }
}

✓ unVirementDe300EurosEstAccepte
✓ unVirementDe1500EurosEstRefuse

Ne pas relever le < tout de suite : la question qui suit le fait.

Avec ce code, un virement de 1 000 € pile est-il accepté ?

return montant < 100000;

Réponse : non. La règle dit « jusqu'à 1 000 € », donc 1 000 € compris. Les deux tests sont verts et pourtant le code est faux : aucun test ne regarde la limite. Les valeurs limites sont là où se cachent les bugs.

Tour 3 · Rouge

On teste la limite


@Test
void unVirementDe1000EurosPileEstAccepte() {
    var plafond = new PlafondVirement();

    assertTrue(plafond.accepte(100000));
}

✗ unVirementDe1000EurosPileEstAccepte
expected: <true> but was: <false>

Le bug est trouvé par un test, avant la production, et non par le service client.

Tour 3 · Vert


class PlafondVirement {
    boolean accepte(long montant) {
        return montant <= 100000;
    }
}

✓ unVirementDe300EurosEstAccepte
✓ unVirementDe1500EurosEstRefuse
✓ unVirementDe1000EurosPileEstAccepte

Un seul caractère change. Les trois tests sont verts.

Refactor

On donne un nom au nombre magique


class PlafondVirement {
    static final long PLAFOND = 100000;

    boolean accepte(long montant) {
        return montant <= PLAFOND;
    }
}

✓ 3 tests passent : le refactor n'a rien cassé

C'est l'étape qu'on saute toujours, et c'est elle qui rend le code lisible. On peut la faire sans peur parce que les tests vérifient qu'on n'a rien cassé.

Ce qu'on a gagné

  • La règle est écrite trois fois, dont deux en langage clair : les noms des tests
  • Le cas limite a été trouvé avant la production
  • Le prochain qui touche à ce code saura tout de suite s'il casse la règle
Revenir à l'histoire du lundi matin : avec ces trois tests, le développeur des virements instantanés aurait vu un test rouge avant de mettre en production.

Mon (vrai) avis sur le TDD

  • Essentiel pour le débogage
  • Pratique pour des POC techniques
  • Compliqué pour réfléchir à une architecture
Pour corriger un bug, écrire d'abord le test qui le reproduit est presque toujours le bon réflexe. Pour concevoir une architecture qu'on ne connaît pas encore, écrire les tests d'abord est plus difficile : on ne sait pas encore quelles classes existeront.

Acte 2

Les tests unitaires

Tester une classe, et seulement elle

PlafondVirement n'avait aucune dépendance, c'était facile. Une vraie classe métier appelle une base, d'autres services, des API externes. Comment la tester seule ?

Faire un virement


class VirementService {
    void virer(Virement virement) {
        String source = virement.source();
        Compte compte = compteRepository.trouver(source);
        if (compte.bloque()) {
            throw new CompteBloqueException(source);
        }
        sepaClient.envoyer(source, virement.cible(),
                virement.montant());
    }
}
La règle à tester : si le compte source est bloqué, on refuse le virement et rien ne part vers le réseau SEPA. Lire le code ligne par ligne avec les fragments. CompteRepository et SepaClient sont injectés par le constructeur.

Le problème

							graph LR
							S[VirementService] --> R[CompteRepository]
							R --> DB[(PostgreSQL)]
							S --> P[SepaClient]
							P --> B[Réseau SEPA]
  • Il faut une base remplie avec un compte bloqué
  • Il faut un réseau SEPA… qui vire vraiment l'argent
  • Et on veut juste tester un if
Demander à la salle comment ils feraient. On veut tester la règle de VirementService, pas PostgreSQL ni le réseau SEPA.

La solution : des faux

							graph LR
							S[VirementService] --> R[Mock CompteRepository]:::faux
							S --> P[Mock SepaClient]:::faux
							classDef faux fill:#3a2f14,stroke:#fde68a,color:#fde68a,stroke-dasharray:6 4
  • Un mock est un faux objet
  • On lui dit quoi répondre
  • On vérifie ensuite comment il a été appelé
Le service ne voit pas la différence : il reçoit un objet qui implémente la même interface. C'est pour ça qu'on injecte les dépendances par le constructeur.

C'est quoi un mock ?

Pause détente avant les quatre étapes avec Mockito.

Étape 1 · Créer les faux


@ExtendWith(MockitoExtension.class)
class VirementServiceTest {

    @Mock
    private CompteRepository compteRepository;
    @Mock
    private SepaClient sepaClient;

    @InjectMocks
    private VirementService virementService;
}
  • @Mock crée un faux qui ne fait rien
  • @InjectMocks crée le vrai service et lui donne les faux
Piège classique : sans @ExtendWith(MockitoExtension.class), les annotations sont ignorées, les champs restent null et le test plante avec une NullPointerException. Par défaut, un mock renvoie 0, null ou une liste vide.

Étape 2 · Programmer le faux


// Given : le compte d'Alice est bloqué
when(compteRepository.trouver("alice"))
        .thenReturn(new Compte("alice", 50000, true));
Virement virement = new Virement("alice", "bob", 1200);

« Quand on te demande le compte d'Alice, réponds un compte bloqué. »

Lire le when / thenReturn à voix haute comme une phrase. Alice a 500 € mais son compte est bloqué ; elle veut virer 12 € à Bob.

Étape 3 · Vérifier le résultat


// When / Then : le virement est refusé
assertThrows(CompteBloqueException.class,
        () -> virementService.virer(virement));

Le service a bien appelé le faux, reçu un compte bloqué, et refusé.

assertThrows exécute la lambda et vérifie qu'elle lève bien cette exception. Si elle n'en lève pas, le test échoue.

Étape 4 · Vérifier les appels


// Then : rien n'est parti vers le réseau SEPA
verify(sepaClient, never()).envoyer(any(), any(), anyLong());

Le résultat ne suffit pas : on vérifie aussi ce qui ne s'est pas passé.

Si quelqu'un déplace l'appel à envoyer avant le contrôle du blocage, l'exception est toujours levée, mais l'argent est parti. Seul ce verify le détecte.

Le test complet


@Test
void refuseLeVirementSiLeCompteEstBloque() {
    when(compteRepository.trouver("alice"))
            .thenReturn(new Compte("alice", 50000, true));
    Virement virement = new Virement("alice", "bob", 1200);

    assertThrows(CompteBloqueException.class,
            () -> virementService.virer(virement));

    verify(sepaClient, never()).envoyer(any(), any(), anyLong());
}
Les trois blocs Given / When / Then restent visibles grâce aux lignes vides.

Le piège : tester le mock


when(additionService.add(2, 3)).thenReturn(5);

assertEquals(5, calculator.calculate(2, 3));
  • calculate ne fait que renvoyer ce que dit le service
  • On vérifie que le mock renvoie… ce qu'on lui a dit de renvoyer
  • Un test unitaire vérifie une décision de la classe : un if, un calcul, un appel ou un non-appel
Ce test est toujours vert, quoi que fasse calculate tant qu'elle passe la main. Demander : quelle décision VirementService prend-elle ? Refuser ou envoyer. C'est ça qu'on teste.

Pour vérifier que rien n'est parti vers le réseau SEPA, de quoi a-t-on besoin ?

  • A. D'un compte de test chez une autre banque
  • B. D'un mock de SepaClient et de verify
  • C. D'un assertEquals sur le retour de virer
Réponse B. C ne marche pas : virer ne renvoie rien, l'effet est un appel à un autre objet. A : jamais de vrai service externe dans un test.

C'est quoi un fake ?

  • Une vraie implémentation, mais simplifiée
  • Exemple : un repository qui stocke dans une Map

class CompteRepositoryEnMemoire implements CompteRepository {
    private final Map<String, Compte> comptes = new HashMap<>();

    void ajouter(Compte compte) {
        comptes.put(compte.numero(), compte);
    }

    @Override
    public Compte trouver(String numero) {
        return comptes.get(numero);
    }
}
Pas de Mockito : c'est une classe normale, écrite une fois et réutilisée dans tous les tests. Dans le test : comptes.ajouter(new Compte("alice", 50000, true)), puis new VirementService(comptes, sepaClient).

Mock ou fake ?

Mock Fake
Comment Mockito, dans chaque test Une classe écrite une fois
Répond Ce qu'on lui a programmé Comme le vrai, en simplifié
Vérifie les appels Oui, avec verify Non
Idéal pour Services externes, appels à vérifier Repositories, données manipulées
Les deux se combinent très bien : un fake pour les comptes, un mock pour le réseau SEPA qu'on veut vérifier.

À vous : le compte d'Alice n'est pas bloqué, 12 € partent vers Bob

Programmez le compte, faites le virement, vérifiez l'envoi SEPA.

Réponse attendue : when(compteRepository.trouver("alice")).thenReturn(new Compte("alice", 50000, false)); virementService.virer(new Virement("alice", "bob", 1200)); verify(sepaClient).envoyer("alice", "bob", 1200); Erreurs fréquentes à regrouper : oublier le when (le mock renvoie null, donc NullPointerException), vérifier avec assertEquals au lieu de verify, ou verify sans les bons arguments.

Acte 3

Les tests d'intégration

Tester avec le framework et la base

Les tests unitaires ont remplacé la base par des faux. Mais qui vérifie que les requêtes SQL marchent, que le JSON est bien lu, que Spring câble bien tout ? C'est le rôle des tests d'intégration.

Le principe

  • Lancer tout ou une partie de l'application
  • Avec une vraie base de données
  • Quelques faux, seulement pour les services externes
La différence avec l'unitaire : on garde les vraies dépendances internes, on ne remplace que ce qui sort de chez nous.

Pourquoi ?

  • Tester la communication entre les classes
  • Tester la communication avec le framework
  • Vérifier les requêtes sur la vraie base
Exemple : une faute de frappe dans le nom d'une méthode de repository Spring Data. Les tests unitaires sont verts, ils utilisent un mock. L'application ne démarre pas.

Alors, que des tests d'intégration ?

  • C'est long à exécuter
  • C'est plus compliqué à maintenir
  • C'est plus compliqué à déboguer
Un test unitaire tourne en millisecondes, un test d'intégration en secondes. Et quand il échoue, la cause peut être dans n'importe quelle couche. Retour à la pyramide : peu de tests d'intégration, beaucoup d'unitaires.

Trois niveaux

Test de… Ce qu'on vérifie Outil
Repository Les requêtes sur la base @DataJpaTest
Service Le framework, la base, les transactions @SpringBootTest
Contrôleur L'URL, le JSON, la sécurité, les codes HTTP @WebMvcTest
On va dérouler le repository et le contrôleur. Le test de service démarre toute l'application, il s'écrit comme le test de repository avec @SpringBootTest.

H2 : la base qui n'est pas PostgreSQL

  • Longtemps, on a utilisé H2 : une base SQL en mémoire
  • Rapide, rien à installer
  • Ce n'est pas PostgreSQL : types, fonctions et SQL diffèrent
  • Test vert sur H2, erreur en production
Exemple : une requête native avec ILIKE ou un champ jsonb marche en production sur PostgreSQL et plante sur H2, ou l'inverse. Le test ne prouve rien sur la vraie base.

Test de repository


@DataJpaTest
@Testcontainers
@AutoConfigureTestDatabase(replace = Replace.NONE)
class CompteRepositoryTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16");

    @Autowired
    private CompteRepository compteRepository;

    @Test
    void trouveLesComptesADecouvert() {
        compteRepository.save(new Compte("alice", -2000));
        compteRepository.save(new Compte("bob", 50000));

        List<Compte> decouverts =
                compteRepository.findBySoldeLessThan(0);

        assertEquals(1, decouverts.size());
        assertEquals("alice", decouverts.get(0).getNumero());
    }
}
Étapes : @DataJpaTest ne démarre que JPA ; replace = NONE l'empêche de remplacer la base par une base en mémoire. @ServiceConnection (Spring Boot 3.1 et plus) donne l'URL du conteneur à Spring, sans configuration. Ensuite un test classique Given / When / Then, sur une vraie base.

Test de contrôleur

  1. @WebMvcTest ne démarre que la couche web
  2. Le service est un mock : on teste le mapping, pas la règle métier
  3. MockMvc simule une requête HTTP, sans vrai serveur
  4. On vérifie le code HTTP et le JSON
Ce qu'on vérifie ici : l'URL, la lecture des paramètres, le JSON produit, les codes d'erreur. La logique, elle, est déjà couverte par les tests unitaires du service.

Test de contrôleur


@WebMvcTest(VirementController.class)
class VirementControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private VirementService virementService;

    @Test
    void renvoieLeVirementEnJson() throws Exception {
        when(virementService.trouver(42))
                .thenReturn(new VirementDto(42, "alice", 1200));

        mockMvc.perform(get("/api/virements/42"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.source").value("alice"))
                .andExpect(jsonPath("$.montant").value(1200));
    }
}
@MockitoBean existe depuis Spring Boot 3.4 ; avant, c'était @MockBean. Même rôle que @Mock, mais le faux est placé dans le contexte Spring. Bon exercice oral : comment tester le cas 404, quand le virement n'existe pas ?

Un test qui démarre l'application avec un PostgreSQL Testcontainers et appelle GET /api/comptes en JSON, c'est un test…

  • A. unitaire
  • B. d'intégration
  • C. end-to-end
Réponse B. Il y a une vraie base et le framework, mais pas de navigateur ni de front : ce n'est pas un end-to-end.

Un client HTTP vers un partenaire

La banque lit le taux de change du jour sur une API externe

Jamais de vraie requête vers un serveur externe dans un test

  • Le serveur peut être lent ou en panne : le test échoue sans raison
  • L'API peut être payante, ou déclencher de vrais virements
Un test doit donner le même résultat à chaque exécution. Un serveur qu'on ne contrôle pas rend le test aléatoire.

WireMock : un faux serveur

							sequenceDiagram
							participant T as Test
							participant C as ChangeClient
							participant W as WireMock
							T->>W: Si GET /taux/USD, réponds {"taux": 108}
							T->>C: tauxDuJour("USD")
							C->>W: GET /taux/USD
							W-->>C: 200 {"taux": 108}
							C-->>T: 108
Le client ne sait pas qu'il parle à un faux : on lui donne juste une autre URL. Le vrai code HTTP est exécuté : la requête, la lecture du JSON, la gestion des erreurs.

WireMock : le test


@WireMockTest
class ChangeClientTest {

    @Test
    void litLeTauxDuJour(WireMockRuntimeInfo wiremock) {
        stubFor(get("/taux/USD")
                .willReturn(okJson("{\"taux\": 108}")));
        var url = wiremock.getHttpBaseUrl();
        var client = new ChangeClient(url);

        long taux = client.tauxDuJour("USD");

        assertEquals(108, taux);
    }
}
Étapes : programmer la réponse, pointer le client vers WireMock, appeler, vérifier. Le vrai intérêt : tester les cas qu'on ne peut pas provoquer chez le fournisseur, comme une erreur 500 ou un délai de 30 secondes. Le taux est en centièmes : 108 pour 1,08.

Acte 4

Les tests end-to-end

Tester comme un utilisateur

Le haut de la pyramide : tout est vrai, du navigateur à la base.

Le principe

  1. Lancer l'application complète : front, back, middlewares
  2. Simuler des actions dans un navigateur
  3. Vérifier ce que l'utilisateur voit

Objectif : vérifier que tout communique correctement

Un robot clique à la place de l'utilisateur. Le test ne connaît pas le code, seulement l'écran.

Un scénario

  1. Ouvrir la banque, connecté en Alice
  2. Choisir Bob comme bénéficiaire
  3. Saisir 1 000 € et valider
  4. Lire « Virement effectué »
La même règle que le TDD, vue depuis l'écran. Ce test vérifie que le front affiche bien ce que l'API décide.

Exemple avec Playwright


test('virement de 1 000 € accepté', async ({ page }) => {
  await page.goto('http://localhost:4200');
  await page.getByLabel('Bénéficiaire')
      .selectOption('Bob');
  await page.getByLabel('Montant').fill('1000');
  await page.getByRole('button', { name: 'Valider' }).click();
  await expect(page.getByText('Virement effectué'))
      .toBeVisible();
});

Selenium et Cypress fonctionnent sur le même principe

Chaque ligne correspond à une étape du scénario. On cherche les éléments comme un utilisateur, par leur rôle et leur texte, pas par leur classe CSS : le test casse moins souvent quand le design change.

Les difficultés

  • Préparer la base
  • Lourd à écrire
  • Lourd à exécuter
  • Quand les exécuter ?
  • Difficile à maintenir
Préparer la base : Alice doit exister, avoir assez d'argent, et Bob être dans ses bénéficiaires. Quand les exécuter : trop lents pour chaque commit, souvent la nuit ou avant une mise en production.

Faut-il en faire ?

  • Oui !
  • Au moins sur les chemins usuels : se connecter, consulter son solde, faire un virement
  • Ils ne remplacent pas les tests manuels
Peu de tests, mais sur ce qui compte : si le virement ne marche plus, la banque ne fait plus son métier.

À retenir

  • Tester, c'est surtout éviter les régressions
  • TDD : rouge, vert, refactor, par petits pas
  • Unitaire : une classe, des mocks et des fakes, tester ses décisions
  • Intégration : une vraie base avec Testcontainers, jamais de vrai serveur externe
  • End-to-end : peu, sur les chemins qui comptent
Revenir à la pyramide une dernière fois. La prochaine fois, l'application grandit : cours middleware.

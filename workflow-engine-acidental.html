Todo sistema tem um
Workflow escondido

Encontre o seu e declare-o com Quarkus Flow

Matheus Cruz

Quem aqui já teve que esperar uma aprovação de outra pessoa dentro de um fluxo automatizado — e essa aprovação podia levar 2 segundos ou 2 dias? Hoje eu quero mostrar como essa espera, sozinha, empurra a gente para construir um workflow engine sem perceber.

Provisionar acesso a um ambiente

Funcionário solicita acesso ↓ Aguarda aprovação do gestor
↓ não aprova Solicitação negada
↓ aprova Provisiona o acesso ↓

Quanto tempo demora essa aprovação?

O código que recebe a solicitação não sabe, e não pode saber, quando a aprovação vai chegar. Esse é o gatilho de tudo: incerteza temporal. O provisionamento em si já dispara uma chamada para a nuvem (AWS) — isso fica implícito no diagrama de propósito, o foco aqui ainda é a espera.

Os três caminhos mais comuns

1. Webhook de callback

2. Coreografia por eventos

3. Polling no banco

Vamos olhar pra cada um de perto.

Os três resolvem o problema. Os três também introduzem uma complexidade de infraestrutura que ninguém queria escrever quando começou a modelar a regra de negócio. Este slide é só o sumário — os três próximos detalham cada caminho e seus problemas.

1. Webhook de callback

Serviço expõe um endpoint HTTP ↓ Aguarda um POST de callback ↓ Correlaciona pelo token salvo em banco ↓ Continua o processo

Pontos fortes

Resposta imediata Padrão HTTP conhecido Não sobrecarrega o banco Simples de implementar
Parece direto: eu exponho um endpoint, o sistema de aprovação me chama de volta quando o gestor decidir. Só que agora eu tenho um endpoint pra proteger, um token pra correlacionar a resposta certa com o pedido certo, e nenhuma garantia de que esse callback vai chegar. É um trade-off: resposta imediata e HTTP conhecido, contra os problemas do próximo slide.

Por que cada problema aqui pesa

Endpoint exposto

Token de correlação

Timeout manual

Reentrega duplicada

Serviço expõe um endpoint HTTP ↓ Aguarda um POST de callback ↓ Correlaciona pelo token salvo em banco ↓ Continua o processo
Só os nomes dos problemas, sem ler nada. Aponte rápido: endpoint pra proteger, token pra correlacionar, timeout que ninguém escreve, reentrega que exige idempotência. Passe adiante.

2. Coreografia orientada a eventos

Aprovação → evento no Kafka/RabbitMQ ↓ Listener no serviço de acesso ↓ Decide o próximo passo

Pontos fortes

Desacoplamento entre serviços Escala bem horizontalmente Reação em tempo real Serviços evoluem independentes
Migrar pra eventos resolve o acoplamento direto do webhook. Mas troca um problema por outro: agora a lógica do processo está espalhada em vários listeners, e nenhum serviço sozinho sabe como o processo inteiro se parece. É um trade-off: desacoplamento e escala, contra os problemas do próximo slide.

Por que cada problema aqui pesa

Listener espalhado

Dead-letter queue

Idempotência

Ninguém vê o processo inteiro

Aprovação → evento no Kafka/RabbitMQ ↓ Listener no serviço de acesso ↓ Decide o próximo passo
Só os nomes: listener espalhado, dead-letter queue sem dono, idempotência e ninguém vendo o processo inteiro. Aponte rápido e passe adiante.

3. Polling no banco de dados

A cada 5 minutos ↓ Busca solicitações pendentes ↓ Tenta provisionar ↓ Atualiza o status no banco

Pontos fortes

Implementação trivial Nenhuma infra nova Fácil de debugar Resiliente a falha de rede
É o caminho de menor resistência — um @Scheduled resolve. Mas repare: a gente trocou "esperar o evento certo" por "perguntar de novo, sempre, sem saber se vale a pena". Na prática, é essa opção que a maioria dos times escolhe. É um trade-off: nenhuma infra nova e fácil de debugar, contra os problemas do próximo slide, e depois a gente vê como ela fica no código.

Por que cada problema aqui pesa

Query desperdiçada

Latência do scheduler

Escala mal

State machine manual

A cada 5 minutos ↓ Busca solicitações pendentes ↓ Tenta provisionar ↓ Atualiza o status no banco
Só os nomes: query desperdiçada, latência do scheduler, escala mal, state machine manual. Aponte rápido — o gancho pro próximo slide é que essa é a opção que mais parece inofensiva.

O código


@ApplicationScoped
public class AccessProvisioningService {

    @Inject DatabaseRepository db;
    @Inject CloudProvisioner provisioner;

    @Scheduled(every = "5m")
    public void pollForApprovedRequests() {
        var pendingRequests = db.findPendingApprovals();

        for (var request : pendingRequests) {
            try {
                provisioner.grantAccess(request.getUserId());
                request.setStatus("COMPLETED");
                db.save(request);
            } catch (Exception e) {
                request.setStatus("FAILED");
                db.save(request);
            }
        }
    }
}
Isso compila. Isso funciona. E isso já é um workflow engine — só que um ruim.

O que esse código realmente é

Transições de estado escritas à mão
Queries desperdiçadas a cada 5 min
Infraestrutura acoplada à regra de negócio

Nós não decidimos construir um workflow engine. Ele apareceu enquanto resolvíamos outro problema.

Esse é o mesmo padrão que aparece em toda base de código que cresce: state machine implícita, espalhada, sem dono.

O que é um workflow, afinal?

"A automação de um processo de negócio, [...] onde documentos, informação ou tarefas são passados de um participante para outro, para uma ação, de acordo com um conjunto de regras procedurais."
— Workflow Management Coalition
Definição da Workflow Management Coalition, traduzida para o que realmente importa.

De acidental pra intencional

Implícito Espalhado Escrito à mão, de novo
→
Intencional Centralizada Declarativa

Por que continuar declarando workflow sem querer, quando dá pra declarar de propósito?

Todo exemplo que vimos até aqui — webhook, eventos, polling — declara um workflow sem admitir isso: implícito, espalhado, escrito à mão de novo a cada vez. A pergunta que fica no ar antes de mostrar o Quarkus Flow é essa: por que não declarar isso de propósito, de um jeito centralizado e declarativo, em vez de deixar acontecer escondido?

Quarkus Flow

Quarkus Flow é Workflow Engine para Quarkus:

  • Gerenciamento de estado, controle de fluxo, chamadas remotas, mensageria, resiliência, observabilidade, etc.
  • Permite Human-in-the-Loop (HITL) e Agentic patterns
  • Permite a criação de workflows duráveis (Durable Workflows)
  • Deixa sua lógica de negócio limpa e orquestra a complexidade para você
Quarkus Flow oferece gerenciamento completo de workflows com estado, resiliência, observabilidade e suporte a padrões modernos como HITL e agentes.

Open Workflow Specification

  • Projeto CNCF Sandbox (candidatando-se à incubação este ano)
  • Ecossistema neutro em relação a fornecedores (vendor-neutral)
  • Integração fluida com arquiteturas modernas
  • Padrões suportados: CloudEvents, AsyncAPI, gRPC, OpenAPI, A2A, MCP e outros
Baseado na especificação Open Workflow da CNCF, que é vendor-neutral e suporta diversos padrões modernos.

Java DSL


@ApplicationScoped
public class EmitFlow extends Flow {
  @Override
  public Workflow descriptor() {
    return workflow("emit", "test")
      .tasks(
        emit("com.petstore.order.placed.v1")
          .source("https://petstore.com")
          .jsonData(Order.class))
      .build();
  }
}
Exemplo de definição de workflow usando Java DSL. Esta é uma forma programática de definir workflows seguindo a especificação Open Workflow.

Reescrevendo com Quarkus Flow


@ApplicationScoped
public class AccessProvisioningWorkflow extends Flow {

    @Inject CloudProvisioner provisioner;

    @Override
    public Workflow descriptor() {
        return workflow("access-provisioning")
                .schedule(on(one("org.acme.access.approved")))
                .tasks(
                    function("provisionAccess", (AccessRequest request) ->
                        provisioner.grantAccess(request.getUserId())),

                    switchWhenOrElse("checkProvisioning",
                        (ProvisionResult result) -> result.isSuccessful(),
                        "notifySuccess", "notifyFailure"),

                    consume("notifySuccess", (ProvisionResult result) -> {
                        System.out.println("Access granted: " + result.getUserId());
                    }).then(FlowDirectiveEnum.END),

                    consume("notifyFailure", (ProvisionResult result) -> {
                        System.err.println("Provisioning failed: " + result.getError());
                    }).then(FlowDirectiveEnum.END)
                )
                .build();
    }
}
Agora que a audiência já viu a sintaxe do DSL, voltamos ao exemplo de provisionamento de acesso do início da palestra e mostramos como ele fica reescrito. Repare no .schedule(on(one(...))): o workflow acorda quando o evento de aprovação chega. Nenhuma thread ficou girando a cada 5 minutos perguntando "já? já? já?".

Apresentação sobre Quarkus Flow, uma workflow engine para Quarkus que ajuda a orquestrar complexidade e trabalhar com agentes de IA.

Todo o sistema começa simples

Todo sistema de software começa de forma simples e elegante.

Um endpoint, um banco de dados e uma regra de negócio

No início, temos apenas um endpoint, um banco de dados e uma regra de negócio simples.

Mas o software nunca permanece simples…

Mas a realidade é que o software nunca permanece simples por muito tempo.

"Complexidade inerente ao Software"

Existem muitas variáveis que se combinam, muitos estados diferentes a serem lidados. Conforme o software cresce, atender a diferentes escalas de usuários introduz novos desafios.

— Brooks, Frederick. No Silver Bullet
Frederick Brooks, em seu famoso artigo "No Silver Bullet", fala sobre a complexidade inerente ao desenvolvimento de software.

O inevitável

Como Thanos disse: "Eu sou inevitável". Assim como no filme, há coisas inevitáveis no desenvolvimento de software.

O inevitável

  • Retries
  • Eventos
  • Filas
  • Timeout
  • Compensação
  • HITL (Human-in-the-loop)
  • Integração com sistemas legados
Conforme o sistema cresce, precisamos lidar com diversos desafios: retries, eventos, filas, timeouts, compensação, interação humana e integração com sistemas legados.

Cuidado com o Workflow engine escondido

  • Se você não tomar cuidado a lógica de coordenação vai, aos poucos, se espalhando por diversas partes do seu código
  • Com o tempo, a lógica de negócio e as preocupações de infraestrutura acabam ficando profundamente acopladas
  • O código fica mais difícil de receber manutenção e surge aquela frase: "Precisamos refatorar o projeto"
Sem perceber, você acaba criando um workflow engine implícito no seu código, espalhado por várias partes do sistema.

Grande bola de lama
(Big Ball of Mud)

O resultado é o anti-padrão conhecido como "Big Ball of Mud" - uma grande bola de lama onde tudo está conectado a tudo.

Exemplo: Compensação na Grande Bola de Lama


public class OrderService {
    @Inject RestClient stockClient;
    @Inject RestClient paymentClient;
    @Inject RestClient shippingClient;
    @Inject EntityManager em;
    @Inject Mailer mailer;

    public void processOrder(Order order) {
        try {
            // Mutate order state - PENDING
            order.setStatus("PENDING");
            em.persist(order);
            
            // HTTP call to stock service
            var stockResponse = stockClient.post("/api/stock/reserve")
                .body(order.getItems()).invoke();
            order.setStockReservationId(stockResponse.getId());
            order.setStatus("STOCK_RESERVED");
            em.merge(order);
            
            // HTTP call to payment service
            var paymentResponse = paymentClient.post("/api/payment/process")
                .header("X-Customer-Id", order.getCustomerId())
                .body(Map.of("amount", order.getTotalAmount()))
                .invoke();
            
            if (paymentResponse.getStatus() != 200) {
                // Compensate: release stock via HTTP
                stockClient.post("/api/stock/release")
                    .body(order.getStockReservationId()).invoke();
                order.setStatus("PAYMENT_FAILED");
                em.merge(order);
                mailer.send(order.getCustomerEmail(), "Payment failed");
                throw new PaymentException("Payment failed");
            }
            
            order.setPaymentId(paymentResponse.getPaymentId());
            order.setStatus("PAYMENT_CONFIRMED");
            em.merge(order);
            
            // HTTP call to shipping service
            var shippingResponse = shippingClient.post("/api/shipping/schedule")
                .body(Map.of("address", order.getShippingAddress(),
                            "items", order.getItems()))
                .invoke();
            
            if (shippingResponse.getStatus() != 200) {
                // Compensate: refund payment via HTTP
                paymentClient.post("/api/payment/refund")
                    .body(order.getPaymentId()).invoke();
                // Compensate: release stock via HTTP
                stockClient.post("/api/stock/release")
                    .body(order.getStockReservationId()).invoke();
                order.setStatus("SHIPPING_FAILED");
                em.merge(order);
                mailer.send(order.getCustomerEmail(), "Shipping failed");
                throw new ShippingException("Shipping failed");
            }
            
            order.setShippingId(shippingResponse.getTrackingId());
            order.setStatus("CONFIRMED");
            em.merge(order);
            mailer.send(order.getCustomerEmail(), "Order confirmed!");
            
        } catch (Exception e) {
            // What if HTTP calls fail?
            // What if compensation HTTP calls fail?
            // What about network timeouts?
            // What about partial failures?
            // How to monitor this mess?
            order.setStatus("ERROR");
            em.merge(order);
            log.error("Order processing failed", e);
            throw new OrderProcessingException(e);
        }
    }
}
Grande bola de lama: estado mutável do Order, lógica de negócio misturada com HTTP, compensação manual via HTTP, sem retries, sem circuit breaker, difícil de testar e manter. Tudo acoplado!

Quarkus Flow

Apresentando o Quarkus Flow - a solução para orquestração explícita de workflows.

O que é um Workflow?

"A automação de um processo, onde os dados são passados de uma tarefa para outra para execução, seguindo um conjunto de regras."
Um workflow é a automação de um processo onde dados fluem entre tarefas seguindo regras definidas.

O que ele veio resolver?

Workflow surgiu para resolver a coordenação de processos complexos com múltiplas etapas, regras, estados e integrações distribuídas. Ele evita que fluxos de negócio fiquem espalhados em if/else, filas, cron jobs e tabelas de controle difíceis de manter, monitorar e recuperar após falhas.

Quarkus Flow

Quarkus Flow é Workflow Engine para Quarkus:

  • Gerenciamento de estado, controle de fluxo, chamadas remotas, mensageria, resiliência, observabilidade, etc.
  • Permite Human-in-the-Loop (HITL) e Agentic patterns
  • Permite a criação de workflows duráveis (Durable Workflows)
  • Deixa sua lógica de negócio limpa e orquestra a complexidade para você
Quarkus Flow oferece gerenciamento completo de workflows com estado, resiliência, observabilidade e suporte a padrões modernos como HITL e agentes.

Open Workflow Specification

  • Projeto CNCF Sandbox (candidatando-se à incubação este ano)
  • Ecossistema neutro em relação a fornecedores (vendor-neutral)
  • Integração fluida com arquiteturas modernas
  • Padrões suportados: CloudEvents, AsyncAPI, gRPC, OpenAPI, A2A, MCP e outros
Baseado na especificação Serverless Workflow da CNCF, que é vendor-neutral e suporta diversos padrões modernos.

Java DSL


@ApplicationScoped
public class EmitFlow extends Flow {
  @Override
  public Workflow descriptor() {
    return workflow("emit", "test")
      .tasks(
        emit("com.petstore.order.placed.v1")
          .source("https://petstore.com")
          .jsonData(Order.class))
      .build();
  }
}
Exemplo de definição de workflow usando Java DSL. Esta é uma forma programática de definir workflows seguindo a especificação Serverless Workflow.

Integração com Langchain4J Agentic

Diferença entre workflows (orquestração predefinida) e agents (decisão dinâmica).

4 padrões base de agentes

@SequenceAgent

Agent A → Agent B → Agent C

um após o outro, a saída vira entrada

@ParallelAgent

→ Agent A Agent B →

ao mesmo tempo, resultados combinados

@LoopAgent

Agent ↻ até a condição

repete até o resultado ser bom o suficiente

@ConditionalAgent

condição? → Agent A Agent B

o caminho depende de uma condição

Os quatro padrões base de sistemas agênticos: Sequence (agentes em série, a saída de um vira entrada do outro), Parallel (agentes ao mesmo tempo, com resultados combinados), Loop (repete um agente até uma condição ser satisfeita) e Conditional (escolhe o agente conforme uma condição).

1º agente: CreativeWriter


@RegisterAiService
public interface CreativeWriter {

    @Agent(name = "Creative writer", description = "Draft a short story about a topic.", outputKey = "story")
    @SystemMessage("""
            You are a creative fiction writer.
            Write short, vivid stories, 4–6 sentences long.
            """)
    @UserMessage("""
            Topic: {topic}

            Write a short story about this topic.
            """)
    String draft(@V("topic") String topic);
}
Primeiro agente da sequência: o CreativeWriter recebe o tópico e escreve o rascunho da história. Repare no outputKey "story": é nele que o resultado é gravado, e é daí que o próximo agente vai ler.

2º agente: AudienceEditor


@RegisterAiService
public interface AudienceEditor {

    @Agent(name = "Audience editor", description = "Adapt story to a target audience.", outputKey = "story")
    @SystemMessage("""
            You rewrite stories to better fit the target audience.
            Keep structure similar but adjust language, tone, and difficulty.
            """)
    @UserMessage("""
            Audience: {audience}

            Rewrite the story below so it is ideal for this audience.
            Story:
            {story}
            """)
    String adapt(@V("story") String story, @V("audience") String audience);
}
Segundo agente: o AudienceEditor recebe a história gerada pelo CreativeWriter (via {story}) e a reescreve para o público-alvo. Ele escreve no mesmo outputKey "story", sobrescrevendo o estado para o próximo agente.

3º agente: StyleEditor


@RegisterAiService
public interface StyleEditor {

    @Agent(name = "Style editor", description = "Adapt story to a specific writing style.", outputKey = "story")
    @SystemMessage("""
            You rewrite stories in the requested writing style
            (for example: fantasy, noir, comedy, sci-fi).
            Keep the meaning, adjust style.
            """)
    @UserMessage("""
            Style: {style}

            Rewrite the story below with this style.
            Story:
            {story}
            """)
    String restyle(@V("story") String story, @V("style") String style);
}
Terceiro agente: o StyleEditor pega a história já adaptada ao público e a reescreve no estilo pedido (fantasia, noir, comédia...). Mesmo mecanismo: lê {story}, grava em "story".

@SequenceAgent


@RegisterAiService
public interface StoryCreatorWithConfigurableStyleEditor {

    @SequenceAgent(outputKey = "story", subAgents = { CreativeWriter.class, AudienceEditor.class,
            StyleEditor.class })
    String write(@V("topic") String topic, @V("style") String style, @V("audience") String audience);
}
E por fim o orquestrador: @SequenceAgent declara os três sub-agentes na ordem de execução (CreativeWriter → AudienceEditor → StyleEditor). Como todos compartilham o outputKey "story", a saída de um vira a entrada do próximo. Um único método write() dispara a sequência inteira.

@ParallelAgent: DinnerAgent


@RegisterAiService
public interface DinnerAgent {

    @Agent(name = "Dinner planner", outputKey = "dinner")
    @SystemMessage("""
            You suggest a single, concrete dinner option in the given city
            for a given mood. Be specific and short.
            """)
    @UserMessage("""
            City: {city}
            Mood: {mood}

            Suggest where to have dinner (one place, one sentence).
            """)
    String suggestDinner(@V("city") String city, @V("mood") Mood mood);
}
Agora o padrão Parallel. O DinnerAgent sugere onde jantar a partir da cidade e do mood. Repare que aqui cada agente tem seu próprio outputKey ("dinner") — diferente do Sequence, eles não encadeiam saída, cada um escreve numa chave separada.

@ParallelAgent: DrinksAgent


@RegisterAiService
public interface DrinksAgent {

    @Agent(name = "Drinks planner", outputKey = "drinks")
    @SystemMessage("""
            You suggest one place for drinks after dinner, matching the mood.
            """)
    @UserMessage("""
            City: {city}
            Mood: {mood}

            Suggest where to have a drink (one place, one sentence).
            """)
    String suggestDrinks(@V("city") String city, @V("mood") Mood mood);
}
O DrinksAgent sugere onde tomar um drink depois do jantar. Mesmas entradas (city e mood), mas escreve no seu próprio outputKey "drinks". Como ele não depende da saída dos outros, pode rodar ao mesmo tempo.

@ParallelAgent: ActivityAgent


@RegisterAiService
public interface ActivityAgent {

    @Agent(name = "Activity planner", outputKey = "activity")
    @SystemMessage("""
            You suggest one short activity to wrap up the evening.
            """)
    @UserMessage("""
            City: {city}
            Mood: {mood}

            Suggest one activity, after dinner and drinks, to finish the evening.
            """)
    String suggestActivity(@V("city") String city, @V("mood") Mood mood);
}
O ActivityAgent fecha a noite sugerindo uma atividade. Terceiro agente independente, com outputKey "activity". Três agentes, três chaves: dinner, drinks e activity.

@ParallelAgent


@RegisterAiService
public interface EveningPlannerAgent {

    @Output
    static EveningPlan toEveningPlan(@V("city") String city, @V("mood") Mood mood, @V("dinner") String dinner,
            @V("drinks") String drinks, @V("activity") String activity) {

        return new EveningPlan(requireNonNullElse(city, "unknown city"), mood != null ? mood : Mood.CHILL,
                requireNonNullElse(dinner, "surprise dinner"), requireNonNullElse(drinks, "surprise drinks"),
                requireNonNullElse(activity, "surprise activity"));
    }

    @ParallelAgent(outputKey = "plan", subAgents = { DinnerAgent.class, DrinksAgent.class, ActivityAgent.class })
    EveningPlan plan(@V("city") String city, @V("mood") Mood mood);
}
E o orquestrador: @ParallelAgent executa os três sub-agentes ao mesmo tempo. Como cada um escreveu numa chave diferente, precisamos combinar os resultados: o método @Output é o post-processor que lê dinner, drinks e activity do escopo e monta o EveningPlan final. Um único plan(city, mood) dispara tudo em paralelo.

@LoopAgent: StyleScorer


public interface StyleScorer {
    @UserMessage("""
            You are a critical reviewer.
            Give a review score between 0.0 and 1.0 for the following story
            based on how well it aligns with the style '{{style}}'.
            Return only the score and nothing else.

            The story is: "{{story}}"
            """)
    @Agent(description = "Score a story based on how well it aligns with a given style", outputKey = "score")
    double scoreStyle(@V("story") String story, @V("style") String style);
}
Agora o padrão Loop. O StyleScorer é o crítico: avalia a história e devolve uma nota de 0.0 a 1.0 indicando o quanto ela está alinhada ao estilo pedido. A nota é gravada no outputKey "score" — é ela que vai decidir se o loop continua ou para.

@LoopAgent: StyleEditor


public interface StyleEditor {
    @UserMessage("""
            You are a professional editor.
            Analyze and rewrite the following story to better fit and be
            more coherent with the {{style}} style.
            Return only the story and nothing else.
            The story is "{{story}}".
            """)
    @Agent(description = "Edit a story to better fit a given style", outputKey = "story")
    String editStory(@V("story") String story, @V("style") String style);
}
O StyleEditor é quem melhora: reescreve a história para ficar mais coerente com o estilo e grava o resultado de volta em "story". Crítico avalia, editor melhora — e a história revisada volta para o crítico na próxima iteração.

@LoopAgent


@RegisterAiService
public interface StyleReviewLoopAgentWithCounter {

    @ExitCondition(testExitAtLoopEnd = true)
    static boolean exit(@V("score") double score, @LoopCounter int loopCounter) {
        loopCount.set(loopCounter);
        return score >= 0.8;
    }

    @LoopAgent(description = "Review the given story to ensure it aligns with the specified style",
            outputKey = "story", maxIterations = 5,
            subAgents = { StyleScorer.class, StyleEditor.class })
    String write(@V("story") String story);
}
E o orquestrador: @LoopAgent executa StyleScorer → StyleEditor repetidamente. A cada iteração, o @ExitCondition lê o "score" gravado pelo crítico: se chegou a 0.8, o loop para e devolve a história. O maxIterations = 5 é a rede de segurança para não iterar para sempre, e o @LoopCounter informa em qual iteração estamos.

@ConditionalAgent


@RegisterAiService
public interface ExpertsAgent {

    @ActivationCondition(MedicalExpert.class)
    static boolean activateMedical(@V("category") RequestCategory category) {
        return category == RequestCategory.MEDICAL;
    }

    @ActivationCondition(LegalExpert.class)
    static boolean activateLegal(AgenticScope agenticScope) {
        return agenticScope.readState("category", RequestCategory.UNKNOWN)
                == RequestCategory.LEGAL;
    }

    @ActivationCondition(TechnicalExpert.class)
    static boolean activateTechnical(@V("category") RequestCategory category) {
        return category == RequestCategory.TECHNICAL;
    }

    @ActivationCondition(UnknownExpert.class)
    static boolean activateUnknown(@V("category") RequestCategory category) {
        return category == RequestCategory.UNKNOWN;
    }

    @ConditionalAgent(outputKey = "response",
            subAgents = { MedicalExpert.class, LegalExpert.class,
                    TechnicalExpert.class, UnknownExpert.class })
    String askExpert(@V("request") String request);
}
Por fim, o padrão Conditional: o @ConditionalAgent declara quatro especialistas (médico, jurídico, técnico e desconhecido), mas só executa aqueles cuja @ActivationCondition retornar true. Cada condição lê a "category" do escopo — via @V ou via AgenticScope.readState, como no LegalExpert — e decide se aquele expert é ativado. É um roteador: a pergunta vai direto para o especialista certo, e a resposta é gravada em "response".
